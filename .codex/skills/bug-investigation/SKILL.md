## 目的

- 症状からいきなり実装に入らず、修正範囲と原因仮説を絞る。
- 誤診のまま広い差分を作るのを避ける。

## いつ使うか

- 再現する不具合はあるが、原因や影響範囲が曖昧なとき。
- UI 症状の背後に API や state 同期の問題がありそうなとき。
- CI failure や runtime error の原因切り分けから始めたいとき。

## 基本フロー

1. 症状、再現手順、期待結果、実際結果を整理する
2. 関連コード経路を絞る
3. 原因仮説と反証条件を整理する
4. 修正が backend 局所か、fullstack 縦断かを決める
5. 修正後に review 観点を確認する

## 例外

- 症状自体が曖昧で、まず再現整理やログ整理が必要な場合は、原因究明を先に置いてよい。

## Subagent 利用方針

- sub-agent 利用が明示的に許可されている場合のみ、次を推奨する。
- 関連経路が曖昧なら `code-mapper` を使う。
- 原因が未確定なら `debugger` を使う。
- 修正がバックエンド局所なら `backend-developer` を使う。
- UI/API 跨ぎの修正なら `fullstack-developer` を使う。
- 修正後のリスク確認には `reviewer` を使う。

## 出力

- 症状要約
- 再現手順
- 主要なコード経路
- 有力な原因仮説
- 推奨される次工程

## 完了条件

- どこを直すべきかが説明できる。
- 少なくとも 1 つの有力仮説と、その確認手段がある。
